# 群内任务协作

任务协作是 `chat`、`cluster`、`swarm` 共用的底层能力，不新增参与模式或侧栏入口。

| 参与方式 | 行为 |
| --- | --- |
| 按需回复（chat） | 被唤起的成员可查阅任务、发协调消息和交接；不通过协作工具自动分派新任务。用户可在面板明确安排后台任务。 |
| 分工协作（cluster） | 负责人可以分派给已在群内、可执行的成员，设置上游任务并汇总交付。 |
| 并行共创（swarm） | 成员共用同一份任务状态、消息与资源占用记录；依赖未完成时等待。 |

## 使用

群聊输入区上方的“任务协作”默认收起，展示进行中任务和待接收交接数量。展开后可安排任务、选择执行成员及依赖、查看结果、确认接收或取消后台任务。前台回复使用原有停止按钮。观察成员只能查看。

所有引擎通过同一个 `collaboration` 宿主工具协调：

- `list` / `inbox`：查本群任务、当前任务 ID 和待处理消息。
- `send` / `blocker`：向指定任务发送信息，带来源并持久化；不会自动创建新任务或唤醒已结束的任务。
- `handoff`：提交 `path`、`version`、`verification` 及说明；接收任务用 `ack` 确认收件。
- `delegate`：在分工协作或并行共创中创建后台任务，指定已有群成员及依赖。
- `reserve` / `renew` / `release`：为连续设备操作保留资源，租期 120 秒，使用结束后释放。
- `complete`：登记前台任务结果；后台任务由实际执行结果决定终态。

消息与任务请求必须使用稳定 `request_id`。相同请求重试复用原记录，内容冲突报错，不重复调用模型。分派限制为每个根任务最多 8 个子任务、最多 3 层；既有后台队列还有全局及群内容量限制。

## 执行与权限

任务、邮箱、交接回执和资源租约保存在既有 `collaboration.db`；执行继续使用 `AsyncWorkStore` 与 `AsyncWorkRunner`，没有第二套调度器。

访问始终通过群对应线程的真实 ACL；任务 ID 不授予权限。分派仅允许已加入、未静音、未被真人接管的执行成员。延迟执行前重查发起人权限和成员状态；取消后的工具调用被拒绝。

AI 分派持久化宿主解析后的读写范围、执行策略及剩余期限，后台执行恢复原权限上限。用户从面板直接安排的任务使用服务端后台执行入口的默认策略。协作消息作为带来源的数据传入，不转写为用户授权。运行期间到达后台任务的消息会在执行返回的安全边界续接原任务，最多 3 次；未被处理的消息仍可通过 `inbox` 获取。前台任务由工具读取邮箱，完成状态可从正式回合日志恢复。

设备互斥在实际处理函数内生效，覆盖执行器、`use_capability`、`execute_skill`、组合技能和临时子代理工具路径。超时返回不会立刻释放仍在执行的处理函数；租约有心跳、过期回收和持有者校验。同一任务的并行设备调用也会被拒绝。

## 边界

- 自动互斥覆盖声明了 `exclusive_resource` 的插件动作和浏览器控制工具。普通 Shell、外部人工操作或未接入的 CAD 适配器不受这套宿主锁控制；适配器应声明共享资源名。
- `verification` 是交付方提供的验证说明，`ack` 是收件回执；二者不等于宿主已经复验文件或验证版本哈希。接收方仍应按任务要求检查文件。
- 租约控制 Echo 内的操作入口，不是操作系统或跨机器分布式锁。
- 群内协作记录不用于发现其他私聊，也不提供跨群消息转发。

前端：在 `frontend` 执行 `pnpm exec vitest run src/components/workspace/collaboration-coordination.test.tsx` 和 `pnpm exec tsc --noEmit`。

独立临时数据库中的页面集成验证覆盖：折叠展开、带版本交接、确认接收、选择成员和依赖、提交后按依赖执行并展示结果。执行者为模拟处理函数，不消耗模型额度，不操作真实 CAD 文件。
