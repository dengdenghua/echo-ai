# 需求打磨与立项评审

项目不要求固定讨论轮数。先明确用户要解决的问题、服务对象、目标成果、本期范围与验证方法；关键方向不清晰时保留需求草案，继续讨论。可逆偏好可作为显式假设，不必强制填写预算和期限。

## 在对话中反复修订

待澄清方案显示“需求草案”，一轮先展示最重要的三个问题，其余问题、当前理解与暂定假设按需展开。输入补充意见后点击“更新草案”，会保留原始目标、逐轮反馈和旧稿，生成并评审新版。已回答的问题应从待确认列表移除，模型假设不会标记为用户确认。

更新草案不会添加成员、建立项目或自动请求批准。需求评审通过后，卡片提供“提交立项审批”；仍可继续修改。有未发送的修改意见时，审批按钮不可用，避免误审旧稿。对话中的普通闲聊不会自动变成项目命令；使用草案内的补充入口可明确将反馈关联到这一版方案。

每份新版草案有独立编号，旧审批不能应用到新版。评审失败或中断时保留已有草案与新反馈，不能借用旧评审直接批准。旧方案没有需求评审记录时，应先更新草案补齐评审。

## 评审做什么

方案生成后，系统再进行一次独立的模型调用，核对用户原始目标和逐轮反馈：范围有无擅自扩大、约束是否遗漏、关键前提是否编造、验收是否可验证。作者自己填写的“评审通过”字段会被丢弃。

这是分开的 AI 评审步骤，可能使用相同模型，不等于人工签字，也不保证模型的判断总是正确。关键问题、缺失交付物或缺失验收标准会阻止进入立项审批。用户授权仍由原有审批流程单独完成。

## 开发者入口

- `/project run <目标>`：准备方案，经过需求评审后按既有流程请求立项授权。
- `/project refine <草案编号> <补充意见>`：修订指定草案，只返回待澄清或待审阅状态。
- `/project review <草案编号>`：提交当前可审批版本；不重新生成方案，不自动启动执行。

状态与历史保存在任务元数据的 `project_initiation` 中：`user_feedback` 为用户反馈，`revisions` 为旧稿快照，`open_questions` 为当前完整问题列表，`changes` 为本轮变更的主要栏目。调用模型时不重复携带全部旧稿全文，但保留最新草案与逐轮反馈。

## 阶段与边界

立项批准后仍沿用阶段执行授权、质量检查和用户交付验收。这里新增的是立项前的多轮需求打磨；尚未把每个阶段升级为由独立专业角色核对实际文件、测试回执与用户试用反馈的完整证据评审。跨阶段退回需求讨论、变更影响传播和统一评审面板仍需后续实现。
