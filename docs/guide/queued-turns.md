# 群线程发言排队

新版会话客户端的 `turn/start` 显式发送 `queueIfBusy: true` 和稳定的 `userItemId`。同一线程繁忙时，服务端按接收顺序登记等待票据，拿到原有跨进程 OS turn claim 后开始执行。不同线程独立运行。仅本人消息 ID 对应的持久收件事件算送达，其他人的 `turn/started` 不算。

等待请求仍属于当前连接：尚未执行时断线或取消，会撤回票据；页面恢复后由用户明确重试。界面保持发送中，收到本人 user item 后才确认送达。已经开始的 turn 按原来的 server-resident 规则继续，重连通过 `thread/resume` 恢复。重复提交同一个 `userItemId` 仍使用既有持久幂等校验，不会启动第二次模型执行；不同内容复用该 ID 会被拒绝。旧客户端省略队列选项时保留原冲突响应。

每线程最多 32 个等待请求，服务端全局最多 256 个；最多等待 30 分钟。容量耗尽或等待超时明确返回 `turn_queue_full` / `turn_queue_timeout`。这些错误、速率限制和连接请求上限不会被无条件自动重试。入队前及执行前检查写权限，等待中被移出协作范围则拒绝执行；审批/沙箱策略和原来的线程删除保护保留。

共享票据只保存线程 ID、随机票据和存活时间，不保存提示词、附件、凭据或执行授权。等待请求续期；崩溃进程留下的票据 15 秒后失效。票据过期只能清理等待顺序，不能抢占活跃 turn 的 OS 锁。状态损坏、锁不可用或写入失败会拒绝开始执行。该队列是共享文件上的跨进程 admission 队列，不是离线持久任务或多 worker pub/sub。

验证包括实际独立进程的 FIFO 顺序和 OS 锁互斥、独立线程、容量上限、取消/断线撤回、权限撤销、失效票据、损坏状态拒绝和 fd 获取期间的取消释放。群成员逐条回复使用另一条有界 mailbox，结果持久化后才通知界面，终态重放去重。
