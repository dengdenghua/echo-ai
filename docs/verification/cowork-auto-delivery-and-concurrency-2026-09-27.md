# 群成员并发与自动交付回归

## 已确认的问题

- 后台 daemon 调用阻塞式 `tick_once()`，在一批任务全部结束后才接收新任务。已有 worker 空位也无法补位。
- 真实日志：Noah 于 22:06:32 开始；Kane 的队列任务于 22:08:21 创建，直到 Noah 于 22:21:32 超时后，22:21:38 才开始。
- 成员结果已进入协调收件箱，但原队长结束当前轮后没有可靠的自动验收入口。
- 将 pending/working 当作交付失败，触发不必要的修复提示和重复规划。

## 改动

- daemon 使用常驻、有界线程池，有空位即接收新任务；完成和新派发都会唤醒调度。初版默认 4 路，后续提高为 16 路（见下文）。有限批次的 drain/tick 接口仍同步返回。
- 每批成员真实终态及结果生成稳定交付 ID，保存到 SQLite。原队长忙时不启动竞争轮；当前轮结束或重新连接时检查待交付批次。
- 汇总使用原发起人、原队长和原执行权限上限。只读观看者或不同账号不会借用凭据执行。自动验收阶段禁止再派发成员任务。
- 只在所有成员都结束后启动一次验收，成功与失败均包含在结果中。前台已读取结果并给出最终答案时，不再重复唤醒。
- 显式停止记录阻止迟到结果自动唤醒；崩溃恢复使用持久化轮次与答案核对，恢复尝试有上限。
- 自动接续不写入伪造的人类消息。正常等待成员改为后台处理中，原协调运行保留 waiting，汇总后更新状态。
- UI 将旧版 `RuntimeError: subagent timed out after 899.985…s` 显示为约 15 分钟超时说明。

## 范围与限制

- 自动交付只对新记录的任务启用，避免重新打开历史已停止或已处理的任务。没有重跑用户现有研究，也没有改变任何群成员。
- 成员可由后台执行器继续运行；队长的自动验收需要原发起人可写的实时连接。离线结果保留，重新连接后接续。
- 有依赖关系的任务及共享桌面/浏览器资源仍遵守原排他约束，不保证所有操作无条件同时执行。
- 本次没有新增真实模型付费调用。执行链使用隔离数据库和可控模型流验证。
- 浏览器恢复页刷新被浏览器安全策略以“不支持的页面协议”为由拦截，未绕过该限制；本次未完成现场点击验证。

## 后续：提高并发容量

- 默认后台并发提高到 16，构造器与应用启动共用默认值，保留 `ECHO_COWORK_RUNNER_MAX_CONCURRENCY` 覆盖；启动日志打印实际配置。
- 修复两个隐藏的 8 项限制：群内单批派工与根任务累计分派都提高到 64。容量统计仍持久化、事务化，重试复用原任务，不重复消耗额度；权限、深度、依赖和设备互斥规则保留。
- 真实线程与隔离 SQLite 队列测试验证默认 16 路、配置 32 路同时进入执行；下一项保持 pending，释放一个 worker 后即补位，其余任务仍在运行。
- 大批派工测试验证 16 / 64 项可入队且可幂等重试；65 项批次及末项为群外成员的批次在派工前拒绝。根任务额度满后重新打开服务仍拒绝新增，已有任务仍可重试。
- 队列、群内协调、子代理并发保护测试：68 passed、1 skipped（既有 Windows SQLite 删除场景）；自动交付与私聊回归：12 passed。合计 80 passed、1 skipped；Ruff 与 diff 空白检查通过。
- 确认无运行中任务后重启后端；启动日志显示 `max_concurrency=16, max_tasks_per_tick=64`，8310 健康接口与 3310 前端均返回 HTTP 200。
- 并发测试使用受控执行函数，没有发起真实模型调用，未测量模型服务在 16 路请求下的吞吐或限流情况。
